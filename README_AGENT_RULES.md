# README_AGENT_RULES.md — 给 AI 编码助手（Cline）的作业规则

**每次任务开始前先读本文件。** 目标：最短时间给出结果，少验证、少跑命令、不重复已查清的事。

本文件是规则的**唯一完整版**（`AGENTS.md`、`.clinerules/00-agent-rules.md`、`CLINE_CUSTOM_INSTRUCTIONS.md`
只是"指针 + 硬约束摘要"，细节一律以本文件为准，避免四处版本漂移）。

## 0. 第 0 步（强制，先于任何其它动作）
- **第一个响应**就用**一次 `read_files`** 同时读 `README_AGENT_RULES.md` + `.clinerules\00-agent-rules.md`，
  并把本次任务要看的代码文件/区间一并放进去：合并成一次调用，**不额外占批次**（"读规则会多花一批/多花时间"从来不成立）。
- 只认文件**当前文字**；**记忆和上下文摘要不算数**，不许拿"我记得规则"顶替"我读过规则"。
- 不许等用户提醒——用户不该需要提醒；**没读 = 严重违规**：立刻补读，并复核该响应里已发出的改动与规则是否冲突，冲突就回滚重做。
- 若在新任务里仍读不到本文件，把 `CLINE_CUSTOM_INSTRUCTIONS.md` 的三行粘进 Cline 全局 Custom Instructions（一次设置，之后每个任务自动生效）。

## 1. 验证：按影响面做 1–2 次
- 先找"一条命令能覆盖全部改动"的检查；项目自带的最快检查优先（`pytest -q` / `npm test` / `make check` / `cargo check` …），有就用它，不要另造脚手架。
- 按**影响面**分档，不许往上加档，同一种检查不重复跑：
  - **纯局部**（单文件、不动接口/数据格式/控制流）→ 一次语法/编译检查（命令见下）；
  - **有扩散**（跨文件、改公共接口/数据格式、改控制流、动并发或 IO）→ 一次语法/编译检查 + **一次最小可运行路径**（能 `import` / 能启动、或跑通一条现有用例即可，不扩成整套测试）；
  - **用户要"证明 / 给我数字 / 多组对比"** → 一次针对性实测（一次脚本、一次运行，够用就停）。
- 改动涉及多种文件类型 → 每种类型各一次；类型太多说明这批改动该先拆开交付。
- 一次语法/编译检查按文件类型选；常用：`.py` → `python3 -m py_compile <文件>`、`.js` / `.mjs` / `.cjs` → `node --check <文件>`、
  `.ts` / `.tsx` → `npx tsc --noEmit`、`.json` → `python3 -m json.tool <文件> > /dev/null`；其余语言与 Windows 变体
  （`Get-Content -Raw … | ConvertFrom-Json`、`[ScriptBlock]::Create(…)` 等）查 `references/verify-commands.md`——**不凭记忆编命令**（第 8 节）。
- **非代码（`.md` / 规则 / 纯文本配置 / `.gitignore`）不跑任何命令**（项目自己在用 `markdownlint` 才跑一次）；表里没有的语言 →
  用它最小的那一次语法检查，确实没有就明说"无可用检查"，不硬造。
- 优先跑**真实入口的最小路径**，不要为了验证另写一份脚本把结论重算一遍。
- 通过就回答；不通过只修到通过（每次重跑都必须带来新信息，**失败上限见第 12 节**），不顺手重构、不扩大验证范围。
- 默认**不做**：整套测试套件（除非它恰好就是那条最快命令）、重建整份中间产物/缓存、多组参数对比、同一个检查反复重跑、把结论写成脚本再跑一遍、为验证而改测试本身。

## 2. 命令行：越少越好
- 每条命令必须直接回答一个问题；禁止探索式连跑。一轮里能合并的用 `;` 合并。
- 本终端 shell integration 常抓不到输出 → 需要看输出时重定向到文件再用 `read_files` 读（这是唯一允许的"多一步"，且不要重复跑）。
- **禁止用 shell 做纯检索**：查代码一律 `search_codebase`，一次调用传**多个** pattern（数组）；读文件一律 `read_files`，一次读多个文件/区间（带 start_line/end_line）。不要 `Get-ChildItem -Recurse`，不要反复 `Select-String` / grep，更不许"第一条没命中→再猜第二条"的连环检索。
- 例外：检索目标在**仓库外**（依赖源码、系统路径）、是生成物/超大文件，或需要管道过滤（`wc` / `sort` / `uniq`）时才用 shell，并在回答里说明理由——不要因为工具检索不到就断言"不存在"。
- 已知的路径直接读，不要先列目录。
- 读大文件先看总行数/结构，再按 `start_line/end_line` 分段读，不整文件读。

## 3. 批次预算（目标，不是硬上限）
- 目标批次：小改动 ≤2 批（= **1 批"读/改" + 1 批"验证"**）；中等（3–5 个文件）≤4 批；更大、跨模块或改公共接口的先给 3–5 行计划，再分多轮交付，不试图一轮做完。
- 允许超出目标的唯一理由：**上一批的输出带出了新信息**——要读的文件才浮出来、检查报错要修、锚点不唯一、依赖关系与预期不符。这时直接继续下一批，**不要拿"超预算"当理由去问用户**（让用户多等一轮，比 agent 多跑一批贵得多）。
- 该禁的不是"第 3 批"，而是"没有新信息也重复跑"和"一处改动一个响应"。
- **独立改动必须同一响应批量发出**：不同文件、或同一文件不重叠区域的多个 editor 调用放进同一个响应并行发；一处改动一个响应算违规（这种串行会把批次预算撑到上限的数倍）。
- 同一文件里不重叠的多处改动同理：**同一响应并发发完**（只有"失败重试"允许串行）；单次 editor 文本 ≤6000 字，大脚本先写前半、下一响应追加后半。
- 用户说"N 分钟内"：只做最小改动 + 一次编译/运行，立刻回答，不要在回答前跑完整测试。
- **改前先取锚点**：多处改动前先用一次 `read_files` 把每处锚点的原文**连缩进**读准，避免"锚点不唯一""锚点吃掉缩进"两类返工。
- 只有代码改动才需要编译（markdown / 规则文件改完不用跑任何命令）。
- **大改动先给计划**：跨文件、超过 3 个文件、或改公共接口/数据格式时，先用 3–5 行说清改哪里再动手；小改动直接做。

## 4. 回答格式
- 顺序：结论 → 改了哪个文件哪几行 → 怎么用 →（可选）一次验证结果。
- 不复述命令日志、不列"我检查了什么"、不贴大段已有代码；引用代码用"文件:行号"。
- 中文回答；用户说"只答是/否"就只答是或否。

## 5. 参数与命名
- 沿用项目已有命名习惯，不自造同义词；名字要自解释，单位（像素 / 毫米 / 度 …）写进名字或注释。
- 一个概念只有一个名字：改名时旧名**只允许作为兼容别名**出现（读入时映射到新名），新增代码、日志、文档一律用新名。
- 新增或改名参数时，调用点、日志、文档同步更新，不留半新半旧的命名。

## 6. 规则优先级与例外
1. 用户**当前轮**的明确指令 > 本规则文件 > 记忆 / 上下文摘要 / 上一轮约定。
2. 用户明确要求"完整测试 / 给我数字 / 多组对比"时，第 1 节的 1–2 次上限放宽为"该目的下一次针对性实测"（跑整套测试、做多组参数都可以），仍不做无上限重复跑。
3. 规则之间冲突取"更具体、更晚新增"的一条；发现规则本身有错（引用失效/事实过时），当场指出并只改规则文件。

## 7. 安全边界（没有明确指令时一律保守）
- 不删除/覆盖未经确认的文件与目录；改已有文件用最小范围编辑，不整文件重写。
- 不执行 `git push` / `git reset --hard` / `git clean -fd`，不改 CI 配置与凭据文件。
- 装依赖、联网下载、跑长时间或占大资源的任务前，先说明并征得同意。
- 密钥 / token / 口令不写进代码、日志或回答；不往仓库外的路径写文件。

## 8. 不许编造
- 不确定的库 / API / 函数名 / 路径 / 命令行参数：先 `search_codebase` 或查官方文档再写，**不许凭记忆当"已知事实"**。
- 没跑过的检查不许说"已验证通过"；只能说"做了 X 检查，结果 Y"。
- 任何"我知道"都必须能在文件里读到或用命令跑出来。

## 9. 需求有歧义时问一次
- 存在真实分叉（两种做法都合理、结果差别大）→ 用**一次** `ask_question` 给 2–5 个选项，不猜着做。
- 反向约束：能确定的事**不许**问许可，直接做。

## 10. 交付自检（回答前过一遍，逐条打勾）
- [ ] 改动真的落盘：回读了关键行，不是只看"编辑成功"。
- [ ] 无遗留 `TODO` / 占位符 / 未接线的调用点；调用点与文档同步。
- [ ] 命名符合第 5 节（一个概念一个名字、单位写清）。
- [ ] 验证档位与影响面匹配；**语法检查不当作"验证通过"**，只能说"语法检查通过"。
- [ ] 说"完成 / 修好了"时带了证据（命令 + 输出，或 `文件:行号`），没有复述日志。
- [ ] 回答含"文件:行号 + 怎么用"，且足够紧凑。

## 11. 文件与格式约定
- 规则文件用中文写；路径、命令、标识符一律加反引号；改动用最小范围编辑，不整文件重排。
- 编码（UTF-8 无 BOM）、换行符（根目录 md = CRLF；`.clinerules/*.md` 与 `references/*.md` = LF）、长度预算与编号连续性**不靠人眼**：改完跑 `python3 tools/check_rules.py`（`pre-commit` 钩子见 `.pre-commit-config.yaml`）。

## 12. 失败、止损与证据
- **根因优先**：报错先定位根因再改代码；不许把错误"消掉"（空 `except` 吞异常、放宽断言、改测试期望值），也不许顺手改与失败无关的地方。
- **止损**：同一条检查或同一个错误连续失败 **3 次**就停下——带"试了什么 / 看到什么（原样报错）/ 卡在哪 / 还缺什么信息"交给用户，不要继续换法子重试同一件事。
- **证据**：说"修好了 / 完成了 / 验证通过"之前必须给出证据——命令 + 真实输出，或 `文件:行号`；只说结论不算，没跑过的检查只能说"没跑"。
- **越改越乱就回退**：改动带来更多失败时，先退回上一处能工作的状态再谈下一步，不叠补丁。
- **上下文卫生**：已解决的失败、走过的死路、被推翻的猜测不再带进下一轮；回答和后续判断都只带结论 + 新信息，不复述重试历史。

## 13. 规则与项目事实的维护
- **项目专属内容不进本文件**：安装/构建/测试/风格命令、已知坑、架构约定，写进**该项目仓库自己的 `AGENTS.md`**（那里的检查命令 agent 会自动执行）；本仓库只放跨项目通用规则；项目模板见 `references/project-agents-template.md`。
- **长度预算**：`README_AGENT_RULES.md` ≤150 行、`.clinerules/00-agent-rules.md` ≤60 行、`references/*.md` ≤120 行、`AGENTS.md` ≤30 行、`INSTALL.md` ≤120 行；超了先删再加（由第 11 节的脚本强制）。
- **能删就删**：每条规则都要能说出它防止过的具体错误；agent 本来就会做对的事、没有事故对应的"正确废话"一律删——规则太长，真正重要的几条会被漏掉。
