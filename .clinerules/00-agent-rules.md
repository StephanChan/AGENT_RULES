# 作业规则（每个任务开始时先读仓库根目录的 README_AGENT_RULES.md）

> 本文件 = 需要自动加载的**硬约束摘要**。规则完整版见 `README_AGENT_RULES.md`（唯一完整版）；
> 冲突时以完整版为准，本文件只允许比完整版**更严格**。

## 第 0 步（强制，先于任何其它动作）
- **第一个响应**就用**同一次 `read_files` 调用**读 `README_AGENT_RULES.md` 和本文件，同时把本次任务要看的
  代码文件/区间一并读进来——合并成一次调用，**不额外占批次**（"读规则多花一批"从来不是理由）。
- 只认文件**当前文字**：记忆、上下文摘要**不算**，不许拿"我记得"顶替"我读过"；不许等用户提醒。
- **没读 = 严重违规**：停下补读，并复核该响应已发出的改动，与规则冲突就回滚重做。

1. **验证按影响面做 1–2 次**：纯局部改动（单文件、不动接口/数据格式）→ 一次语法/编译检查；
   有扩散（跨文件 / 改公共接口 / 改数据格式 / 改控制流）→ 再加**一次最小可运行路径**（能 `import`、能启动、
   或跑通一条现有用例）；用户要"证明/给我数字"→ 一次针对性实测。同一种检查不重复跑，多种文件类型各一次。
   完整命令表（含 Windows 变体）见 `references/verify-commands.md`——它不在 `.clinerules/` 里，按需读，别凭记忆编命令。
   默认**不做**：整套测试（除非它恰好是最快那条命令）、重建整份中间产物/缓存、多组参数对比、反复重跑同一检查、
   把结论写成脚本再跑、为验证而改测试。通过就回答；不通过只修到通过（失败上限见第 10 条），不顺手重构。
2. **命令越少越好**：每条命令直接回答一个问题，能合并的用 `;` 合并；需要看输出就重定向到文件再
   `read_files`，不要重复跑同一个命令。已知路径直接读，不先列目录。**检索一律走 `search_codebase`**
   （一次传**多个** pattern）/ `read_files`（一次读多个文件/区间），**禁止用 shell 做纯检索**
   （`Select-String`、`Get-ChildItem -Recurse`），不许"没命中→再猜一条"连环 grep。唯一例外：目标在**仓库外**
   （依赖源码、系统路径）、是生成物/超大文件、或需要管道过滤时才用 shell，并说明理由。
3. **批次预算（目标，不是硬上限）**：小改动 ≤2 批（= 1 批"读/改" + 1 批"验证"）；中等（3–5 个文件）≤4 批；
   更大、跨模块或改公共接口的先给 3–5 行计划再分多轮。**上一批的输出带出了新信息**（要读的文件、检查报错要修、
   锚点不唯一）就**直接继续下一批，不要拿"超预算"当理由去问用户**；该禁的是"没有新信息也重复跑"。
   用户说"N 分钟内"→ 只做最小改动 + 一次编译/运行，立刻回答。**独立改动必须同一响应批量发出**：不同文件、
   或同一文件不重叠区域的多个 editor 调用放在同一个响应里并行发，禁止一处改动一个响应；markdown/规则文件
   改完不用跑命令。
   **改前先取锚点**：动手前用一次 `read_files` 把每处锚点的原文**连缩进**读准；
   同一文件里不重叠的多处改动一律在同一个响应并发发 editor（除了"失败重试"，没有"等上一处改完"的正当理由）；
   editor 单次文本 ≤6000 字，超了先写前半、下一响应追加后半（这是唯一允许的串行）。
   **大改动先给计划**：跨文件、超过 3 个文件、或改公共接口/数据格式时，先用 3–5 行说清改哪里再动手。
   **优先级**：用户当前轮的明确指令 > 本文件/README 规则 > 记忆/历史约定（README 第 6 节）。
4. **回答格式**：结论 → 改了哪个文件哪几行 → 怎么用 →（可选）一次验证结果。不复述命令日志、不贴大段已有代码。
   中文回答；用户说"只答是/否"就只答是或否。
5. **参数与命名**：沿用项目已有命名习惯、不自造同义词，名字自解释且带单位；一个概念只有一个名字，
   改名时旧名只允许作为兼容别名，新增代码/日志/文档一律用新名。完整说明见 `README_AGENT_RULES.md` 第 5 节。
6. **安全边界**（摘要）：不删/不覆盖未确认的文件，不整文件重写；不跑 `git push` / `reset --hard` / `clean -fd`；
   装依赖、联网、长任务前先问；密钥不进代码与回答。完整条款见 `README_AGENT_RULES.md` 第 7 节。
7. **不许编造**（摘要）：不确定的库/API/路径/参数先 `search_codebase` 或查文档，不许凭记忆当"已知事实"；
   没跑过的检查不说"已验证通过"。完整条款见第 8 节。
8. **需求有歧义**：真实分叉用一次 `ask_question`（2–5 选项），不猜着做；能确定的事不问许可（第 9 节）。
9. **交付自检**：回答前按第 10 节的清单逐条打勾（落盘 / 无 TODO / 命名 / 验证档位 / 证据 / 紧凑）。
10. **失败、止损与证据**：报错先找根因再改，不许把错误"消掉"（吞异常、放宽断言、改测试期望值）；同一条检查/同一个
    错误连续失败 **3 次**就停下，带"试了什么 / 看到什么 / 卡在哪"交给用户；已解决的失败与死路不带进下一轮；
    声明"修好了/完成了/验证通过"必须给证据（命令 + 输出，或 `文件:行号`），只说结论不算；**回显与预期不符**
    （该"编辑"却回"已创建"、路径变了）就立刻停下核对真实路径与状态，别接着改下一处。
11. **规则与项目事实**：项目专属命令/坑写进**该项目自己的 `AGENTS.md`**，本文件只放通用规则；本文件 ≤60 行、
    `README_AGENT_RULES.md` ≤150 行；每条规则要能说出它防止过的错误，否则删。完整说明见 README 第 12、13 节；
    改完规则跑 `python3 tools/check_rules.py`（编码 / 换行 / 长度 / 编号，第 11 节）。
